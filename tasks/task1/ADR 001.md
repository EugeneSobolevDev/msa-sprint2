### <a name="_b7urdng99y53"></a>**Название задачи: Целевая архитектура сервиса **Hotelio**" **
### <a name="_hjk0fkfyohdk"></a>**Автор: Соболев Е.В.**
### <a name="_uanumrh8zrui"></a>**Дата: 10.12.2025**
### <a name="_3bfxc9a45514"></a>**Функциональные требования**
Hotelio — онлайн-платформа для бронирования отелей и апартаментов. 
У неё около 1 млн зарегистрированных пользователей и основной трафик приходится на поиск и бронирование жилья.
Цель: Поэтапный переход от монолитной к микросервисной архитектуре, с применением паттерна Strangler Fig, — вынос сервисов по одному компоненту,
Это позволит упростить масштабирование, снизить время выхода фич, повысить отказоустойчивость и упростить независимую разработку разных команд.

## 🚨 Текущие проблемы
1. **Сложность сопровождения**
    - Любое изменение требует понимания всей кодовой базы
    - Невозможно менять один модуль, не затрагивая другие

2. **Низкая масштабируемость**
    - При пиковых нагрузках (например, на бронирование) нельзя масштабировать только нужный компонент
    - Производительность неравномерна

3. **Невозможность гибкой разработки**
    - Разные команды не могут работать независимо
    - Трудно внедрить быстрый CI/CD

4. **Ограничения на фронтенде**
    - REST API монолита слишком универсален и плохо адаптируется под разные платформы
    - Нет поддержки BFF

5. **Сложности с запуском новых фичей**
    - Большой риск ошибок из-за плотной связанности
    - Тестирование требует понимания всех зависимостей

**Описание архитектуры**
Специализированные BFF для каждого клиентского типа, единые бизнес-сервисы, event-driven коммуникация через Kafka.

Основные компоненты и их ответственность:
1. Frontend Layer (Клиентские приложения)
Web Application
Технология: Node.js/React
Протокол: GraphQL Subscriptions через WebSocket
Ответственность: Веб-интерфейс для пользователей, PWA приложение

Android Application
Технология: Android Studio (нативное или Flutter)
Протокол: GraphQL Subscriptions
Ответственность: Мобильное приложение для Android

IOS Application
Технология: Flutter (кроссплатформенное)
Протокол: GraphQL Subscriptions
Ответственность: Мобильное приложение для iOS

Partner API
Технология: Клиентская реализация (любая)
Протокол: REST API/Websocket + API Key аутентификация
Ответственность: Интеграция партнеров

2. BFF Layer
BFF Web & BFF Android & BFF IOS
Технология: Java
Протокол: GraphQL Server + WebSocket для subscriptions, Kafka consumer для оповещений
Ответственность: GraphQL/WebSocket соединения с фронтендом

BFF Partner API
Технология: Java
Протокол: REST API/WebSocket + API Key, Kafka consumer для оповещений
Ответственность: REST/WebSocket соединения с фронтендом

3. Booking Service (Ядро системы)
Технология: Java
Протокол: gRPC, Kafka
Ответственность:
- Создание, изменение, отмена бронирований
- Координация всех проверок (пользователь, отель, промокоды)
- Расчет финальной цены
Базы данных:
- Booking DB (PostgreSQL): Основные данные бронирований
- Reviews DB (Mongo): Отзывы и рейтинги
- Promo DB (Mongo): Промокоды и скидки

Kafka топики (consumer):
- hotel.available - Отель доступен для бронирования
- hotel.not_available - Отель недоступен
- booking.cancel.demand - Запрос пользователя на отмену бронирования
- booking.cancel.confirmed - Отель подтвердил отмену
- payment.completed - Бронирование оплачено

Kafka топики (producer):
- booking.created - Создано бронирование (ожидает подтверждения отелем)
- booking.ready_to_pay - Готово к оплате (подтверждение отеля получено)
- booking.cancelled - Бронирование отменено
- booking.confirmed - Бронирование подтверждено (оплачено)

4. User Service
Технология: Java
Протокол: gPRC
Ответственность:
- Аутентификация и авторизация
- Черные списки
- История действий
Базы данных:
- User DB (PostgreSQL). Профили и статус пользователей, учетные данные

5. Hotel Service
Технология: Java
Протокол: gRPC, Kafka
Ответственность:
- Каталог отелей и номеров, поиск и фильтрация, доступность
- Ценообразование
Базы данных:
- Hotels DB (PostgreSQL): Данные об отелях, номерах, доступность
Kafka топики (consumer):
- booking.created - Бронирование создано
- booking.cancel.demand - Запрос на отмену бронирования

Kafka топики (producer):
- hotel.available - Отель доступен для бронирования
- hotel.not_available - Отель недоступен
- payment.refund - Возврат средств

6. Payment Service
Технология: Java 
Протокол: gRPC, Kafka
Ответственность:
- Инициирование и обработка платежей
- Интеграция с платежными шлюзами
- Финансовые отчеты

Kafka топики (consume):
- payment.refund - Запрос на возврат платежа

Kafka топики (produce):
- payment.completed - Платеж принят

Внешнии интеграции:
Платежные шлюзы

7. Notification Service
Технология: Java
Протокол: Kafka
Ответственность:
- Централизованная доставка уведомлений
Внешние интеграции:
- SMS Distribution System: Провайдер SMS рассылок
- E-mail Distribution System: Провайдер e-mail рассылок

**Обоснование выбора технологического стека**
Язык программирования для backend: Java.
Язык программирования для frontend: Node.js + React.
Брокер сообщений: Kafka.
Соответствие высоким требованиям производительности и надежности, а также экспертизе текущей команды.

GraphQL для клиентских API.
- Клиент запрашивает только нужные поля
- Один запрос для сложных страниц
- Эволюция схемы без версионирования
- Автодокументация через схему
- Real-time через Subscriptions

WebSocket для real-time коммуникации.
Высокий уровень гибкости, безопасности и производительности.

gRPC для внутренней коммуникации.
- Протокол буферы (бинарный, компактный)
- HTTP/2 (multiplexing, compression)
- Автогенерация клиентов/серверов
- Встроенные retry, deadlines, tracing
- Streaming для real-time данных

PostgreSQL для основных реляционных БД.
Соответствие высоким требованиям производительности и надежности, а также экспертизе текущей команды.

MongoDB для NoSQL.
Высокий уровень гибкости, скорости и простоты разработки.

**Недостатки, ограничения, риски**
- Высокая сложность разработки тестирования и сопровождения
- Сложность мониторинга большого количества топиков Kafka
- Необходим контроль за консистентностью данных
